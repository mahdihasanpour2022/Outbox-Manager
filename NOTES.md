# Implementation Notes

When a message fails, later messages for the same recipient pause behind it. The user can retry the failed message, while messages for every other recipient continue independently. I chose this policy because automatically delivering a follow-up after its prerequisite failed can preserve transport order while breaking conversational meaning. Pausing is conservative and visible: it protects context and leaves the decision with the user. The alternative would provide more throughput for that recipient, but risks delivering a confusing partial conversation.

The queue is implemented as independent sequential recipient lanes. Zustand owns serializable message, selection, requested-send, and announcement state; a separate scheduler owns promises, abort controllers, and attempt tokens. That split keeps network resources out of UI state and localizes the rules that the brief says will change. Tailwind CSS provides the responsive visual system without a component library. Vitest is used only for deterministic verification of transitions, same-recipient ordering, cross-recipient concurrency, failure blocking, cancellation, and stale completions.

For a production-scale system, I would move delivery authority to a backend with durable queues, idempotency keys, persistence across reloads, bounded global concurrency, retry/backoff policy, structured error reasons, and observability. For very large outboxes I would add pagination or virtualization while retaining stable item identity and focus restoration. Given the take-home time box, state is intentionally in memory and verification concentrates on the highest-risk scheduling behavior; a longer project would also add browser-level keyboard/accessibility tests and automated accessibility scanning.
